# iPMS — Work Order Management Design

> **Superseded in part** by [2026-09-25-work-orders-in-qc-design.md](2026-09-25-work-orders-in-qc-design.md): work orders now live in `qc`, not as `project` tasks. Decisions W1, W2 and W6 and the status-sync section below describe the earlier design.

**Status:** Implemented
**Date:** 2026-09-24 (revised 2026-09-25)
**Parent spec:** `2026-09-22-qc-template-management-design.md` §1 (sub-project 2)

## 1. Scope

Assigning published QC checklists to sites as **work orders**, following them through
the field engineer's submission and QC's review, and managing them while open.

**In:** batch assignment (one checklist, one person, many sites); a workspace-wide queue
across projects; the Project ID (DU) on every work order; write-time validation of the
template and of the assignee's access; reassign, reschedule and cancel; a per-work-order
timeline; `qc.submission.*` → task status sync; submission-side assignee enforcement.

**Out:** "Responsible Company" (users carry no company yet); work order edit of type or
checklist (cancel and re-assign instead); the ONGOING transition (set by the mobile app
through `PATCH /tasks/:id` when work starts); a review UI (sub-project 3).

## 2. Decisions

| # | Decision | Rationale |
|---|---|---|
| W1 | A work order is a `project` `Task` with `workOrderType` set | Engineer lists, qc's checklist lookup and dashboard counts see it unchanged |
| W2 | `Task.taskTypeId` is nullable | A work order is raised against a checklist, not a project task type; it credits no milestone |
| W3 | The **Project ID is the DU** and is shown with every site | Site codes repeat across projects (antenna upgrade, power upgrade); only the project tells them apart. No separate DU field |
| W4 | Creation is a **batch**: `siteIds[]`, one work order per site, all or none | Rolling a checklist out to a cluster is the common case; replaces one-form-per-site "continuous creation" |
| W5 | Names are generated by the service: `[Type label]Site name` + optional note | Every work order on a site reads the same way; a batch needs no per-site naming |
| W6 | `templateName` is snapshotted on the task | The queue renders without a cross-service join; qc owns templates |
| W7 | `project` validates the template via qc `GET /internal/templates/:id`, forwarding the caller's token | Same pattern as qc's `TaskLookupClient`; no shared secret |
| W8 | Type ↔ category: `QUALITY_*` needs a `QUALITY` template, `EHS_*` an `EHS` one | A Quality check on an EHS checklist is meaningless |
| W9 | The assignee must reach every site through the replicated scope projection | Otherwise the work lands on a list they cannot open |
| W10 | qc refuses a submission from anyone but the task's assignee, for another checklist, site or project, for a cancelled task, or while one is pending/approved | Submissions now move task status, so they must be the assignee's own |
| W11 | Status sync is event-driven: qc writes `qc.submission.submitted` / `.reviewed` to its outbox; project consumes on one durable per subject | Same outbox → JetStream pattern as iam's scope events |
| W12 | Sync writes are conditional on `attemptNo`, never on arrival order | The two subjects travel separately; a review can precede its submission, a redelivery can follow a newer fact |
| W14 | Work orders and tasks are one list, on the workspace dashboard only | They are the same thing; a project tab repeating the dashboard would be a second place to look |
| W13 | `iam GET /users/directory` (name, employee code, active) gated by `task.view` | QC Managers assign spot checks but lack `user.view`; narrower than `/users` |

## 3. Data

`task` gains `workOrderType`, `templateName`, `currentAttemptNo`, `cancelReason`,
`createdAt`; `taskTypeId` becomes nullable. New `work_order_event` (`taskId`, `kind`,
`at`, `actorId`, `detail` jsonb): `CREATED`, `REASSIGNED`, `RESCHEDULED`, `CANCELLED`,
`SUBMITTED`, `APPROVED`, `REJECTED`, written in the same transaction as the change.

### Status sync

| Fact | Applies when | Sets |
|---|---|---|
| submitted (attempt n) | not CANCELLED/COMPLETED, and n > current attempt | REVIEWING, current submission/attempt |
| reviewed, approved | not CANCELLED, and n > current, or n = current and not yet reviewed | COMPLETED, `actualCompletionAt` = review time |
| reviewed, rejected | as above | RECTIFYING |

The timeline entry is written once per task, kind and submission, even when the status
write is a no-op, so history is complete whatever order facts arrive in.

## 4. API

| Route | Permission | Notes |
|---|---|---|
| `GET /work-orders?projectId&status&view&workOrderType&assigneeId&q&page&limit` | `task.view` | Across visible projects. `view`: `open` / `overdue` / `closed`. Rows include `project {id, code, name}` and `site`. `counts` per status plus `OVERDUE`, ignoring status/view |
| `GET /work-orders/:id` | `task.view` | With `events` |
| `PATCH /work-orders/:id` `{assigneeId?, plannedCompletionAt?}` | `task.assign` | 409 when closed; 400 when the new person cannot reach the site |
| `POST /work-orders/:id/cancel` `{reason}` | `task.cancel` | Conditional on still being open |
| `POST /projects/:id/work-orders` `{workOrderType, templateId, siteIds[], assigneeId, plannedCompletionAt, note?}` | `task.create` + `task.assign` | `{ created: WorkOrder[] }` |
| `GET /projects/:id/work-orders/assignable` | `task.assign` | `{userId, wholeProject, siteIds}[]` |
| qc `GET /internal/templates/:id` | `qc_template.view` | Not reachable through the gateway |
| iam `GET /users/directory` | `task.view` | Includes inactive users, flagged |

Open work is ordered by due date, closed work by completion. The gateway gains the
`/api/v1/work-orders` prefix; project reads `QC_INTERNAL_URL`.

## 5. Web

Designed around the coordinator's questions — *what is late, what is next, where does
everything stand* — rather than as a wide data grid.

- **Work orders dashboard** (`/work-orders`): the one place work orders — a
  project's tasks — are listed. A project has no *Tasks* or *Work orders* tab; its
  overview links to the dashboard filtered by its project ID
  (`/work-orders?projectId=…`), and the old `/projects/[id]/tasks` and
  `/projects/[id]/work-orders` URLs redirect there. The dashboard has a
  completion bar across statuses; filter pills with counts (Open, Overdue, In review,
  Needs rework, Completed, Cancelled, All); search, project, check type and *Assigned to
  me*. Open views group rows by due date (Overdue, Due today, Next 7 days, Later). Each
  row: a Quality/EHS self/spot mark, the name, the **project ID chip** beside the site,
  the checklist, the person, a relative due phrase, and the status. Everything is links
  and GET forms.
- **Composer** (`/work-orders/new`): three steps — *what* (type tiles, then searchable
  checklist cards with size and critical counts), *where* (project, then a filterable
  multi-select of its sites), *who and by when* (only people who can open every chosen
  site; quick due dates; an optional note). A sticky summary shows how many work orders
  will be made, their names, and the checklist outline.
- **Detail** (`/work-orders/[id]`): facts including Project ID (DU); the timeline;
  reassign, move date, cancel with reason; the checklist outline.
